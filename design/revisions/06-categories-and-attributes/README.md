# Option C refined: categories and attributes

The user selected option C and proposed replacing subcategories with attributes
throughout the catalog. This revision explores that direction with two mockups
generated by editing the original C image using built-in `image_gen.imagegen`.
Open [the gallery](index.html); [manifest.json](manifest.json) links the PNGs and
exact generation prompts. These are design proposals, not screenshots of an
implemented taxonomy migration.

## Model

Keep broad categories. Refine their contents through relevant typed attributes,
without a second category-navigation level. A type is a filter that can combine
with size, sheet count and other specifications; it does not appear in the
breadcrumb or a separate row of navigation tiles.

| Category | Type attribute examples | Other relevant attributes |
| --- | --- | --- |
| Cuadernos | Cuadriculado, Rayado, Composición, Caligrafía, Croquis, Liso | Formato, Número de hojas; Cuadrícula or Orientación where applicable |
| Escritura | Grafito, Bolígrafo, Destacador, Corrector, Goma, Sacapuntas | Dureza and Incluye goma for graphite pencils, when data exists |
| Arte y dibujo | Croquera, Block, Lápices de colores, Plumones, Témperas, Acuarelas, Pincel, Plasticina | Formato, hojas, dimensions, block specifications or Número de colores, according to type |
| Geometría | Regla, Escuadra, Transportador, Compás | Largo for rulers |
| Papeles y cartulinas | Papel, Cartulina, Goma EVA | Only measured or curated attributes present in the catalog |
| Pegado y corte | Pegamento, Tijeras, Cinta adhesiva | Peso for glue, Tipo de punta for scissors, when populated |
| Organización | Carpeta, Archivador, Forro, Estuche | Relevant populated specifications |
| Aseo | Papel higiénico, Pañuelos, Jabón | Relevant populated specifications |
| Otros | Optional, curated values only | No invented type or empty mandatory filter |

For notebooks, “Tipo de cuaderno” is more accurate than “Tipo de hoja”: the
existing labels mix ruling and use. Preserve Croquis and Liso as distinct values,
and do not infer a page pattern for Composición or Caligrafía. The existing
classification is retained as information, with a different interaction model.

## Interaction

- Breadcrumb: `Catálogo / Cuadernos` or `Catálogo / Geometría`. “Cambiar categoría”
  opens the category chooser. There is no subcategory row in any category.
- The left drawer contains category-relevant attributes. Selecting a type is
  optional; users may begin with another applicable attribute.
- Common selections remain when compatible. Changing from Cuadriculado to Rayado
  clears an incompatible grid-spacing filter and hides that control. Formato and
  Número de hojas remain available where supported by data.
- Selecting Regla exposes Largo. Notebook controls disappear in Geometría.
- Selected chips stay above results, including when the drawer is collapsed.
  Type and other filters can be cleared independently; empty results retain
  recovery actions. The working list remains visible and unchanged when browsing
  another category.
- Filters remain single-choice per attribute, matching the current typed query
  model. Counts respect the other active filters and ignore their own selection.
- The notebook mockup shows Caligrafía disabled with zero matches under
  Universitario. This proposes stable category choices with unavailable values
  visible; the current endpoint may omit such unselected zero-count values.
  This display behavior must be aligned in a later implementation.

## Evidence used in the mockups

Cuadriculado + Universitario gives the five existing variants: 100 hojas/7 mm,
100/5, 80/7, 80/5 and 60/7. Under the Universitario filter, type counts are
Cuadriculado 5, Rayado 2, Composición 1, Caligrafía 0, Croquis 1 and Liso 1.
No store inventory, pricing or new catalog products are implied.

The geometry seed has one Regla, Escuadra, Transportador and Compás. Selecting
Regla leaves one result with its actual Largo of 30 cm. The existing writing
supplies have no populated hardness/gum data, so those values are not invented
for a mockup.

## Implementation implications

This is a data-model change as well as a navigation change. Attribute assignment
currently depends on `catalog.subcategory_attributes`. Implementation will need
category-level assignments and conditional applicability, together with matching
updates to custom-item forms, administration, import validation and search.

Use a new migration after 004, which is already applied and must remain immutable.
Backfill type attributes from existing classifications while preserving item IDs,
canonical keys, aliases, review status, source-product links and published list
snapshots. Update the importer to write types as attributes and retain its existing
canonical identity keys, so imported products do not create duplicate supplies.
Administrative or imported classifications that cannot be mapped reliably need
review rather than guessed values. Existing data must not be deleted merely to
remove its old navigation role.

The current turn only adds design assets and notes. The migration, API, importer
and application changes remain part of the implementation work after design
exploration. The images illustrate layout; actual desktop density, focus and
responsive behavior must be checked in the rendered application.
